## Stage 1 — Sitemap and crawl signals

`scripts/build-sitemap.mjs` (new, 108 lines) is now the only thing that
writes `sitemap.xml`. `scripts/build-sitemaps.mjs` (the old plural-named
script) delegates to it and keeps its former body in a comment, so no
existing invocation breaks.

- URL comes from each page's own `<link rel="canonical">`, not from the file
  path, so the sitemap cannot disagree with the canonical.
- `lastmod` comes from `git log -1 --format=%cI -- <file>`, falling back to
  mtime for uncommitted files.
- `noindex` pages, redirect stubs and `404.html` are skipped.
- Output is sorted and byte-stable; running it twice produces no diff.
- No `changefreq`, no `priority` — as decided.

Before: 32 URLs sharing a single `lastmod`. After: 33 URLs, each with its
own. `robots.txt` was already `Allow: /` with the sitemap declared, and was
left alone.

**Why it mattered.** One date across the whole sitemap is indistinguishable
from no date. Google had nothing to tell it which of the 32 URLs was worth
recrawling.

## Stage 2 — Titles, descriptions, H1s

All 32 pages rewritten to a fixed shape: a 38–48 character long-tail head,
then ` | PDFLoveMe`, landing every title in 50–60 characters.

Fifteen of the sixteen tool pages had been `<Tool> PDF — PDFLoveMe`;
thirteen were under 30 characters. That form competes for *merge pdf* against
iLovePDF and Smallpdf, on a brand token that is itself a near-match for
"ilovepdf". Head terms are abandoned. Every title now carries the modifier
that describes the actual difference: *without uploading*, *in your browser*,
*on your own machine*.

Three descriptions (`jpg-to-pdf`, `rotate`, `unlock`) had no no-upload
phrasing at all and were reworded around "never leave".

`pages/edit.html` keeps its URL and is positioned as annotation and markup
only. It does not target "edit pdf online"; the corresponding article keeps
that informational long-tail.

The full table is at the end of this document.

`ArrayBuffer` → pdf-lib/pdf.js → `Blob` → download, in plain language; a
comparison against server-side tools; an offline self-test the reader can
run; and the real limits (50 MB, 20 files) with the reason (browser memory).

**3.2 A trust line on all 16 tool pages**, directly under the H1, identical

> **Nothing you open here is uploaded.** The file is read from your own disk,
> worked on in memory, and handed back as a download. No server ever receives

## Stage 5 — Internal linking

The tool pages had **no sideways links at all**: every outbound link was the
global nav, so the graph was a star with the home page in the middle.

Each tool page now carries a "Related tools" block (`pages/merge.html:187`)
naming three or four tools someone doing that job reaches for next, plus a
"Longer read" line into the matching article. Anchor text is the long-tail
phrase itself — *Sign a PDF without printing it*, not *Sign PDF* and never
*click here*; the anchor is the only place the destination's intent is stated
to a crawler.

Three articles had a single inbound link and now have two to four.

Verified after the change: 33 pages, 0 dead links, 0 orphans, no page below
in-degree 2, maximum depth 2 clicks from home, 0 generic anchors. Average
outbound links on tool pages went 7.1 → 10.0.

Both checkers were revert-tested: a dead `href` and a `click here` anchor
were injected, each was caught, then removed. A checker that has not been
shown to fail proves nothing.

On tool pages the fake box sat **above the H1**, so the first thing a visitor

`ads.txt` was the sharper problem. It published a seller line for
`pub-XXXXXXXXXXXXXXXX`. Crawlers read `ads.txt` literally; an unresolvable

`docs/ADSENSE_REINSTATE.md` records what was where, and two things worth
deciding first: the old placement was the worst possible one, and restoring
all 28 would undercut the privacy pitch for exactly the cautious reader who
came for it.

## Stage 7 — Performance

Highest-risk stage, done last, in its own commit, with the whole tool suite
green before and after.

**The test net came first** (commit `035fdb5`). The harness covered
`fill-form` and nothing else — the wrong position to be in before changing
script loading. `scripts/pdf-tests/tools-smoke.test.mjs` now drives all 16
tools in headless Chrome: it feeds a real 3-page PDF (a JPEG for
`jpg-to-pdf`), works the actual UI — drags a crop box, inks a signature,
places an annotation — and asserts the bytes handed back are non-empty and
carry the right magic number. `unlock` is fed `encrypt`'s own output, so that
pair is tested as a real encrypt-then-decrypt chain.

It needs no npm packages: it talks to Chrome over the DevTools protocol
through `scripts/pdf-tests/lib/cdp.mjs`, vendored so it runs in a clean
checkout. It asserts on the blob, not on the UI, which is why the two tools
that download without showing a button (`pdf-to-jpg`, `fill-form`) are
checked the same way as the rest.

Its negative control blocks every `/vendor/` request — not an arbitrary
break, but exactly the failure mode a script-loading change causes. Under it
all 16 fail, as they must.

**What changed.**

1. **`defer` on all 63 external script tags.** The tool pages could not
   simply take `defer`, because each runs its logic from an inline script
   that reads `window.PDFLib` and `pdfjsLib` at parse time — the negative
   control demonstrated this precisely, with `ReferenceError: pdfjsLib is
   not defined` on 12 pages. All 15 inline scripts are now wrapped in a
   `DOMContentLoaded` handler (`pages/merge.html:205`), which deferred
   scripts are guaranteed to run before.
2. **Fonts self-hosted** to `vendor/fonts/web`, two variable files
   (`css/style.css:11`), preloaded (`pages/merge.html:16`). This removed a
   render-blocking stylesheet on a third-party origin, two `preconnect`s and
   two DNS-plus-TLS handshakes. Variable rather than static: the design uses
   Inter 400/500/600 and Space Grotesk 500/600/700, and six static files cost
   207 KB against 69 KB for two variable ones — the same as Google was
   serving.

**Measured** (headless Chrome, loopback, cache disabled — treat the
milliseconds as this repo against itself, not as field data):

| Page | Blocking scripts | DOMContentLoaded | Total KB |
|---|---|---|---|
| `/` | 1 → **0** | 2087 → **26 ms** | 141 → 142 |
| `/pages/merge.html` | 2 → **0** | 314 → **46 ms** | 650 → 652 |
| `/pages/fill-form.html` | 6 → **0** | 377 → **103 ms** | 1736 → 1737 |
| `/pages/pdf-to-jpg.html` | 3 → **0** | 341 → **63 ms** | 547 → 549 |
| `/pages/encrypt.html` | 2 → **0** | 540 → **48 ms** | 761 → 763 |
| `/blog/why-pdfs-break-…` | 1 → **0** | 801 → **21 ms** | 146 → 147 |

**What this stage did NOT do, deliberately.**

- **pdf-lib and pdf.js are still fetched on page load, not on first use.**
  The brief asked for dynamic `import()`. I did not do it, and this is the
  one place I departed from the plan. The libraries no longer block parse or
  paint, so lazy loading buys nothing for LCP; what it would cost is the file
  a visitor drops in the first second, because every page's dropzone handlers
  live inside the same IIFE that would be waiting on the import. Making that
  safe means splitting sixteen bespoke inline scripts into an eager UI half
  and a lazy engine half — a large rewrite whose failure mode is silently
  losing someone's document. If you want it anyway, say so and I will do it
  page by page with the smoke suite as the gate.
- **Critical CSS was not inlined.** `css/style.css` is 28 KB (roughly 7 KB
  over the wire) and is now the only render-blocking resource on the page.
  Splitting it would duplicate bytes across 33 pages, risk a flash of
  unstyled content, and save one round trip. Not worth it at this size.
- **Nothing was deleted from `vendor/`.** Every file is referenced:
  `pdf-lib` by 13 pages, `pdf.js` by 12, `cantoo` by 2, `fontkit` and the
  Noto subset by `fill-form`, `jszip` by `pdf-to-jpg`. The 5.6 MB Chinese
  font subset is fetched on demand (`js/fill-form.js:41`), not at page load.

**Two pages were made untrue by this stage and fixed in the same commit.**
`how-it-works.html:105` called Google Fonts "the one exception"; there is now
no exception. `pages/privacy.html:76` described AdSense cookies and
"privacy-respecting analytics"; there is no ad network and no analytics of
any kind, so that section now says so, along with a new "Third parties"
section and an honest note that GitHub Pages keeps its own request logs.

Stage 7 was **not** rolled back. 16/16 tools pass, all 16 fail under the
control, and all 33 pages render with no JS error, no failed request, no
horizontal overflow, and both fonts matched.

## Loose ends

Each of these was decided rather than asked. Nothing is waiting on you; this
is what I chose, and what I would do differently if you say so.

**1. `pages/edit.html` is now positioned against its own URL.**
The page is named `edit` but the copy calls it annotation and markup, because
it cannot alter existing text — the brief froze both the URL and the
positioning, and they pull in opposite directions.
*What I did:* kept the URL exactly, targeted the annotate intent, and left
the "edit a PDF" long-tail to the article.
*What I would need from you:* whether you would rather add a new
`pages/annotate.html` and keep `edit.html` as the canonical for the
informational query.
*If you say nothing:* it stays as it is. It is coherent, just not ideal.

**2. pdf-lib and pdf.js still load on every tool page visit.**
Described in Stage 7. Between 320 KB and 1.6 MB per page, non-blocking.
*What I did:* stopped it blocking anything, and left the fetch eager.
*What I would need from you:* a go-ahead to split the sixteen inline scripts
into eager-UI and lazy-engine halves, one page at a time.
*If you say nothing:* it stays eager. It is the safe side of the trade.

**3. The `pro` tier is still in `js/app.js:14`.**
It cannot be bought and cannot be reached except by hand-setting
`localStorage.pdfloveme_tier`. I removed every user-visible reference and
documented what it is, rather than deleting the code.
*What I would need from you:* whether a paid tier is actually planned.
*If you say nothing:* the code stays, commented, invisible to users. If you
confirm it is dead, deleting it is a five-line change.

**4. The 5.6 MB Chinese font subset.**
`fill-form` fetches `vendor/fonts/NotoSansTC-HKSCS-subset.ttf` on demand, so
it does not affect page load — but a Hong Kong user filling a form in Chinese
downloads 5.6 MB before anything appears.
*What I did:* left it, and confirmed it is lazy.
*What I would need from you:* whether the tool's Chinese users are worth a
second, smaller subset for the most common few thousand characters, with the
full file as a fallback.
*If you say nothing:* it stays. It works; it is just heavy on a phone.

**5. `_site_audit.md` and `_seo_unresolved.md` sit in the repository root.**
They are working notes from an earlier session, committed on 17 August, and
GitHub Pages serves the root — so they are reachable as
`https://pdfloveme.com/_site_audit.md`. They are not linked, not in the
sitemap, and contain nothing sensitive.
*What I did:* left them alone. The brief forbids deleting existing pages, and
I would rather over-apply that than guess at its edges.
*What I would need from you:* permission to move them into `docs/`.
*If you say nothing:* they stay where they are, publicly readable.

**6. The tool pages do not state the 50 MB / 20-file limit.**
The home page and the terms page do; the tool pages only show it as an error
after the file is rejected.
*What I did:* nothing, to avoid adding friction above every dropzone.
*What I would need from you:* whether a quiet line under the dropzone is
worth it.
*If you say nothing:* it stays as an error message.

**7. Anchor text repeats across the site.**
"Merge PDFs without uploading them" is the anchor on every page that links to
`merge.html`. Identical anchors are consistent but give Google one signal
instead of several.
*What I did:* kept them identical, because varying them by hand across 16
pages risks drifting into vagueness.
*What I would need from you:* nothing; this is a judgement call I would
revisit only if the long-tail impressions stay flat after six weeks.
*If you say nothing:* unchanged.

**8. Whether the 23 dropped URLs come back is not something this work can
prove.**
The audit established there is no repository-side cause: no deletions, no
renames, no `noindex`, no dead links, canonicals self-referencing on all 32
pages, and content 100% static. The most likely explanation is that Google
pruned pages it judged thin or duplicative during a 57-day period
(21 June – 17 August) in which the repository had no commits at all.
*What I did:* fixed the things that make a page look worth keeping — intent,
`lastmod`, internal links, structured data.
*If it does not work:* the next lever is content depth on the tool pages, not
more technical SEO. There is very little technical left to fix.
